# Research: Alert Limits on Charts

**Date**: 2026-11-22 | **Spec**: [spec.md](spec.md) | **Plan**: [plan.md](plan.md)

What the code does today, and the decisions the plan rests on. Paths are from the
repository root.

## What exists

- **A deployment's definition is the automation graph.** For a DAG automation the
  runtime's compile step returns the workflow itself (`services/runtime/internal/app/dag.go`),
  and Laravel stores it unchanged in `automation_deployments.definition`
  (`Domain/Automation/Services/DagDeployment.php`). Its shape is
  `contracts/rules/v2/workflow.schema.json`: `bindings` (role, device, parameter,
  unit), `nodes` and `edges`. The column is `json`, and the row is immutable.
- **Running and suspended are both "applied".** `automation_workflows.applied_deployment_uuid`
  names the deployment the runtime confirmed. A suspension sets `stopped_reason` on
  that deployment and `deployment_status = 'suspended'`
  (`WorkflowDeploymentService.php`, `Workflow::executionSuspended`). A deactivation
  clears `applied_deployment_uuid`. A pending change leaves the applied pointer where
  it was until the runtime answers.
- **Node semantics** (`services/runtime/internal/dag/evaluator.go`, `registry.go`):
  `compare.v1` has `operator` (`gt`, `gte`, `lt`, `lte`, `eq`) and `value`;
  `hysteresis.v1` turns on above `activate_above` and off below `clear_below`;
  `window.v1` aggregates `count`, `sum`, `min`, `max` or `average` over
  `duration_seconds`; `convert.v1` converts between `C`, `F`, `K`, `Pa`, `kPa`, `bar`,
  `m`, `cm` with one linear formula, and the compiler refuses a conversion whose
  `from` is not the connected parameter's unit; `sustained.v1` requires `seconds`; `boolean.v1`
  is `and` or `or`; `branch.v1` sends the condition to a `true` or a `false` port, and
  the `false` port carries the opposite outcome; `join.v1` passes each input through
  to the output of the same name; `cooldown.v1` passes the condition through.
- **Alerts already have a device list.** `automation_alert_devices` holds "the devices
  the alert concerns" and is indexed by device. `AlertProjector` attaches one device to
  a workflow alert: the first binding. `AlertQuery::filtered` finds alerts for a device
  by the first binding in the deployment's JSON, or by this list. The site filter does
  the same.
- **A binding's unit is the parameter's unit** at the time the automation was
  written (`apps/portal/src/automation/bindings.ts`), and a panel source's unit is the
  parameter's unit when the dashboard was saved (`DashboardDefinition.php`).
- **Time series panels** (`apps/portal/src/dashboards/TimeSeriesPanel.tsx`) build one
  chart option with `timeSeriesOption` (`packages/charts/src/timeSeries.ts`). Panel
  thresholds are already dashed horizontal lines with a label; alert periods are
  shaded areas from `useDeviceActivity`, which asks for alerts per device every 30
  seconds. The legend is an HTML list under the chart.
- **Panel settings are an allow-list per panel type**
  (`Domain/Dashboards/Services/DashboardDefinition.php`). A time series panel accepts
  `sources`, `columns` and `workflow_uuid`; any other key is refused.
- **The portal knows automation permissions**: `organization.capabilities.automation`
  has `view`, `manage` and `activate` (`packages/api-client/src/alerts.ts`).
- **The public API has an OpenAPI description** (`contracts/openapi/openapi.json`),
  generated by `php artisan contract:export` and checked by `contract:check`
  (ADR-016).
- **Local API tests default to SQLite**, CI runs them on PostgreSQL. Existing JSON
  queries go through the query grammar so both work.

## Decisions

### R1. Laravel works the limits out from the stored definition

- **Decision**: a service in `Domain/Automation` walks the applied deployment's graph
  and returns the limits. Nothing is asked of the runtime.
- **Rationale**: the definition is already in Laravel's database and is immutable, so
  the answer cannot go stale. Dashboards keep working while the runtime is down
  (principle I: clients talk to Laravel; Laravel owns every public API).
- **Alternatives considered**: an internal runtime endpoint beside the evaluator, as
  `location-overview` uses. Rejected: every dashboard refresh would depend on the
  runtime, for data Laravel already holds. A table of limits written at activation.
  Rejected for this version: it needs a backfill and a second copy to keep right; R4
  keeps the cost low without it.

### R2. One shared fixture keeps PHP and Go in agreement

- **Decision**: `contracts/rules/v2/alert-limits.fixture.json` lists automations with
  the limits expected from each, including every "left out" case. The PHP resolver is
  tested against all of it. A Go test in `services/runtime/internal/dag` runs the
  evaluator on the cases it can probe (direct, converted, inverted, hysteresis) with a
  reading just either side of each limit and asserts the alert changes as the fixture
  says.
- **Rationale**: the resolver is a second reading of the graph, in another language.
  The fixture is what proves FR-009 and SC-002 (principle IV).
- **Alternatives considered**: PHP tests only. Rejected: nothing would fail if the
  runtime's meaning of a node changed.

### R3. The walk, and when it gives up

- **Decision**: start at each `action.alert.v1` node and follow its input upstream.
  - `sustained.v1` adds its seconds to "held for" and continues.
  - `cooldown.v1` continues.
  - `boolean.v1` marks the limit as one of several conditions and follows both inputs.
  - `branch.v1` continues; arriving from its `false` port inverts the comparison.
  - `compare.v1` and `hysteresis.v1` end the condition part. From there the numeric
    input is followed: `join.v1` through the same port; one `window.v1` with `min`,
    `max` or `average` records the treatment; `convert.v1` is undone on the value;
    `source.parameter.v1` ends the walk at a binding.
  - Anything else gives up on that branch, and so does any node type the resolver does
    not know: `math.v1`, `constant.v1`, `geofence.v1`, a `count` or `sum` window, a
    second window, a conversion whose `from` is not the binding's unit or whose units
    are not of one family, an inverted `eq`, and a binding that is not a number.
- **Rationale**: FR-007 forbids approximating. Giving up on unknown node types means a
  node added to the runtime later draws nothing until the resolver and the fixture
  learn it.
- **Inversion**: `gt` becomes `lte`, `gte` becomes `lt`, and the reverse. For
  hysteresis the two values swap roles.
- **Conversion**: the eight units convert with a positive linear formula, so the side
  of the limit is unchanged. The converted value is rounded to 10 significant digits.
- **Alternatives considered**: solving `math.v1` with a constant (reading × 2 > 50).
  Left for a later version; the spec lists arithmetic as left out.

### R4. One request per dashboard, no cache

- **Decision**: the portal asks once for all the devices of a dashboard's time series
  panels (up to 100 device identifiers per request, in chunks beyond that) and repeats
  every 45 seconds. The API loads the organization's applied deployments in one query
  and walks them in memory.
- **Failure**: a failed request is retried once. If the retry fails the panels remove
  their limit lines and say limits are unavailable, until a request succeeds
  (FR-017a). Keeping the last limits on screen was rejected: a limit that may have
  changed would be shown as current (principle VI).
- **Rationale**: FR-016 allows a minute. One request per dashboard keeps the cost flat
  as panels are added. An organization's applied automations are expected to be few
  (tens to low hundreds) and their graphs small; this has not been measured.
- **Alternatives considered**: a request per panel or per device, like
  `useDeviceActivity`. Rejected: twenty panels would walk every graph twenty times. A
  PostgreSQL JSON predicate to load only deployments that bind the asked devices.
  Rejected for now because local tests run on SQLite; it is the first step if
  measurement shows a need. Memoising per deployment in the cache. Not needed at this
  size; the deployment is immutable, so it can be added without invalidation.

### R5. Alerts for every device: fill the list that already exists

- **Decision**: `AlertProjector` attaches every device the deployment reads, not only
  the first binding. A data migration sets the list of existing workflow alerts to
  the devices their snapshots read. `AlertQuery`'s device and site filters already
  search this list; the one change is that their older match on the first binding in
  the snapshot now applies only to an alert that lists no device.
- **Why the filter changed after all** (found while building): the first-binding match
  would still find an alert from a commanded device when that device is the first
  binding, which FR-026 forbids. It cannot simply go, because an alert whose bound
  device names no device record lists nothing and is found only that way.
- **Snapshots that name no source** (older and partial ones) read their first binding,
  as before, and the migration leaves their alerts alone.
- **"Reads"** means bindings named by a `source.parameter.v1` node, and the single
  `binding` of a geofence rule. A binding used only by `action.command.v1` is not read
  (FR-026).
- **Rationale**: the list is indexed and is already the stated truth for which devices
  an alert concerns. No query changes, and FR-029 is a backfill.
- **Consequences to test**: the alert's `devices` and `devices_total` in API responses
  now list every read device (the main `device_uuid` stays the first binding). A device
  move ends active alerts through this list (`Alert::scopeEndingWithMoved`), so moving
  the second read device now ends the alert too; this matches the automation being
  suspended when any bound device moves (spec 031, FR-036).
- **Alternatives considered**: a JSON predicate over every binding in `AlertQuery`.
  Rejected: unindexed, not portable to the local test database, and it could not
  exclude commanded devices without also reading the nodes.

### R6. The setting is one optional key on the panel

- **Decision**: `alert_limits: false` in a time series panel's `config` turns the
  lines off. The key is absent when on. The allow-list for time series gains it; the
  server never adds it.
- **Rationale**: FR-020 and SC-006: saved dashboards stay byte-for-byte the same, and
  export, import, templates and `DashboardRewrite` carry the key without knowing it.
- **Alternatives considered**: `alert_limits: true` written on every panel. Rejected:
  it rewrites saved dashboards.

### R7. Drawing

- **Decision**: `timeSeriesOption` gains `limits`, drawn as mark lines in the warning
  colour with their own dash pattern and a heavier stroke than panel thresholds; a
  limit that clears is dotted and lighter. The label carries the automation's name and
  the comparison, which a panel threshold never has. The value axis is not given the
  limits, so it keeps following the readings.
- **The 8 drawn** (FR-015): after merging limits that differ only by device, the ones
  nearest the range of the drawn values; ties by value.
- **Off the chart**: after layout the panel reads the value axis extent from the chart
  and marks, in the legend, limits beyond it as above or below the chart.
- **Legend**: a second list under the series, "Alert limits", one row per limit:
  automation name (a link when `capabilities.automation.view`), the device when the
  panel has more than one, comparison and value with unit, treatment, and a `Status`
  from the kit when suspended.
- **Rationale**: FR-011 needs a difference that is not colour alone; the dash pattern,
  the stroke and the label are three.
- **To confirm while building**: that ECharts clips a mark line outside the axis
  extent and does not widen the axis for it; a designer's screenshot pass on the line
  styles in light and dark themes, at phone width and in kiosk mode.

### R8. Who may ask

- **Decision**: the same check as the alerts list: `DevicePermission::VIEW` in the
  organization. Device identifiers that are not this organization's devices return
  nothing. The response includes the automation's name and identifier, which alerts
  already show to the same people.
- **People without device access**: a role can hold `Dashboard.view` without
  `Device.view` (`docs/features/dashboards.md`). The portal does not ask for limits
  when `capabilities.devices.view` is false, and treats a refusal as "no limits", so
  such a person is not told limits are unavailable (FR-022a).
- **Rationale**: FR-022. The link to the automation is offered by the portal only when
  the person has `Workflow.view`; the automation's own endpoints still enforce it
  (FR-024).
