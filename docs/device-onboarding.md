# Device onboarding

The proposed vendor MQTT adapter and physical device replacement work is recorded in [Device integration and replacement plan](device-integration-plan.md).

Use **Devices → Add device**, or **Connect a device** from a published device profile.

1. Choose direct Sparkplug B or an existing gateway, select a published profile, and name the device.
2. For a direct publisher, download the connection ZIP. It includes `device-config.json`, `ca.crt`, and `quickstart.md`. Manual connection settings are also available, with a masked password. For an existing gateway, configure its downstream Device ID; shared gateway credentials are not exported.
3. Start the publisher. The wizard waits for the birth message and lets you match announced metrics to profile parameters. Samples at this point are previews.
4. Review validation and activate. Completion requires runtime acknowledgement and good-quality stored readings for every reported parameter.

**Save and exit** preserves a created setup. Resume it or retrieve its kit from the device's **Connectivity** tab. Before creation, the first-page draft is kept in the current browser session. Starting another device creates a fresh request identity.

## Connection configuration

- Direct devices publish their measurements as an Edge Node using NBIRTH/NDATA and a scoped MQTT credential. The kit includes group, host, edge-node, and client identifiers.
- Authentication uses username/password over verified TLS. The public CA verifies the broker; it is not a client certificate. Mutual TLS client certificates are not generated by this flow.
- Configure `DEVICE_MQTT_PUBLIC_URL` with a reachable `ssl://` hostname covered by the broker certificate. `localhost` works for a simulator on the broker's computer, not separate hardware.
- Configure `DEVICE_MQTT_CA_FILE` with the public CA path readable by the API. The Devices Compose overlay mounts the existing public CA read-only. Never mount or distribute a CA private key.
- Creating a direct setup and downloading credentials require connection-management access; device creation, mapping, and activation require the corresponding device permissions. Kit responses are private and non-cacheable.
- The API accepts an idempotency UUID and retries failed broker provisioning without allocating another device or changing its identity.

## Water-meter simulator

Prepare the additive local example profile from `apps/api`:

```sh
rtk proxy php artisan devices:prepare-water-meter-profile --organization=acme-manufacturing
```

Select **Water meter (simulator)** in onboarding. Extract the downloaded ZIP into a private directory. From the repository root, use the existing simulator Python environment:

```sh
rtk proxy .local/devices/python/bin/python tooling/simulators/water_meter.py \
  --config .local/devices/water-meter/device-config.json \
  --state-file .local/devices/water-meter/state
```

The default flow is 12 L/min (`--flow-rate` can change it). Total volume starts at 1,000 L, integrates elapsed running time, and persists across process restarts. The publisher waits for Sparkplug host availability, sends typed NBIRTH metrics and alias-based NDATA updates, handles rebirth, and sends NDEATH on graceful shutdown. Keep both state files when restarting. Downtime is not added to accumulated volume.

### Runtime recovery performed during verification

An existing SQL automation checkpoint referred to an older JetStream incarnation and prevented runtime startup. Before recovery, the runtime schema and processed-event ledger were saved privately under `.local/onboarding-recovery/`. Every one of the 501,751 retained committed telemetry event IDs was compared with that ledger; all were already processed. Only the checkpoint's stream identity and sequence were reconciled to the verified current stream, after which runtime readiness passed. Automation execution state, history, and deduplication records were preserved; no previously processed automation actions were replayed by the reconciliation.

This was an evidence-based local recovery, not a general reset procedure. A different stream gap requires its own audit; do not copy the checkpoint values to another environment. No production deployment was performed.
